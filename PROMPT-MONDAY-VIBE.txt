 0. INSTRUCCIÓN PRINCIPAL (pegar esto en monday Vibe)
--------------------------------------------------------------------------------
Build a React app for monday.com called "Etoile Flow — Allocation Matrix".
It is a single screen where the US team sees, for every open wholesale order
and every SKU, how much is still uncovered and which source of stock can cover
it: warehouse stock, each container in transit, each purchase order.
Read all data with the monday SDK (monday.api GraphQL) from the boards and
columns listed below. Do not create boards or columns. For now the app is
read-only: it never writes to monday.
Use the attached stylesheet exactly (same fonts, colours, spacing, class names).
Follow sections 1 to 9 of this document exactly.

 1. ARQUITECTURA
--------------------------------------------------------------------------------
- React (componentes funcionales + hooks). Sin librerías de UI.
- Acceso a datos: monday-sdk-js.
    const monday = mondaySdk();
    const transport = (query, variables) =>
      monday.api(query, { variables }).then((res) => {
        if (res.errors?.length) throw new Error(res.errors.map(e => e.message).join(" | "));
        return res.data;
      });
  En Vibe NO hay token ni proxy: el SDK usa la sesión del usuario.
  (En la versión local, el mismo "transport" es un fetch a /api/monday, un proxy
  de servidor que guarda el token. El resto del código es idéntico.)
- Tres capas:
    a) data layer: consultas + normalización (sección 3)
    b) engine: funciones puras de cálculo, sin I/O (sección 4)
    c) UI: componentes (secciones 5 a 8)
- Componentes:
    App
     ├─ Sidebar           (menú lateral colapsable, con contadores)
     ├─ Topbar            (breadcrumb + buscador)
     └─ AllocationMatrix  (pantalla)
         ├─ barra de frescura + botón Refresh
         ├─ MetricCards   (4 tarjetas, 2 son filtros)
         ├─ ControlsBar   (View by: "Wholesale order" + Expand all / Collapse all)
         ├─ ShowFilters   (chips Show)
         ├─ Legend        (leyenda estática)
         └─ MatrixTable   (grupos = órdenes, filas = SKUs, columnas = fuentes)
     └─ Toast

--------------------------------------------------------------------------------
 4. REGLAS DE CÁLCULO (engine, funciones puras)
--------------------------------------------------------------------------------
Todo se calcula en la app a partir de los datos crudos. Nada derivado se guarda.

4.1 Conjuntos
  - Órdenes abiertas: group ∈ {topics, group_mm1730xq} y region = "US".
  - Contenedores en tránsito: group "topics", Location US, Packing List ≠ "Done",
    por ETA ascendente (sin ETA al final).
  - Contenedores llegados: Location US y Packing List = "Done".
  - POs activas: region US; solo subitems con Qty Outstanding > 0; por ETA.
  - Filas: subitems de órdenes abiertas con Outstanding > 0.

4.2 Total de cada fuente, por SKU
  - Warehouse:  max(0, US qty).
  - Contenedor: Σ Qty de sus subitems con ese SKU (puede haber uno por PO).
  - PO:         max(0, Σ Qty Outstanding del SKU − Σ Qty de subitems de contenedores EN
                TRÁNSITO con ese SKU y PO Reference == nombre de la PO).
                → las unidades de una PO que ya viajan en un contenedor se cuentan UNA
                sola vez, en el contenedor (nunca PO + contenedor a la vez).

4.3 Etapa de cada entrada confirmada
  - warehouse: el SKU existe en Master SKU                          → WAREHOUSE
  - intransit sobre contenedor en tránsito con ese SKU               → IN TRANSIT
  - intransit sobre contenedor LLEGADO (Done) con ese SKU:
      recorrer las líneas por Cancel Date ascendente; libre del warehouse del SKU =
      US qty − entradas warehouse − entradas Done ya pasadas a warehouse.
      Si ese libre ≥ 50 % del To ship de la línea → pasa a WAREHOUSE (y consume
      warehouse). Si no → sigue IN TRANSIT hasta que se cumpla (se re-evalúa en
      cada carga).
  - po sobre PO activa con ese SKU y outstanding > 0                 → PO
  - Cualquier otro caso (fuente borrada / archivada / sin ese SKU)   → HUÉRFANA:
    no cuenta como asignada ni descuenta libre; se suma aparte para el pie.
  No se recortan reservas por lo ya despachado (decisión del cliente: lo corrige el
  usuario al entrar a la línea).

4.4 Por línea
  To ship = US Qty Outstanding · Allocated = min(Σ entradas no huérfanas, To ship)
  Left = max(0, To ship − Allocated)

4.5 Libre por fuente
  Usado(fuente, SKU) = Σ qty de entradas no huérfanas de TODAS las órdenes abiertas
  (también líneas con Outstanding 0), según su etapa. Libre = max(0, Total − Usado).
  Oferta libre del SKU = libre warehouse + Σ contenedores en tránsito + Σ POs.

4.6 Faltante (Impossible)
  Por SKU: max(0, Σ Left del SKU − oferta libre). Por línea: max(0, Left − oferta libre).

4.7 Drafts (no se guardan, no reservan, no cuentan en métricas)
  Líneas por Cancel Date ascendente (vacía al final). Cada una usa lo libre menos lo ya
  propuesto a líneas anteriores:
    1. Warehouse, si su libre cubre AL MENOS EL 50 % del Left: toma min(libre, Left).
       Si no, se saltea.
    2. Contenedores en tránsito por ETA. 3. POs por ETA.

4.8 Métricas (4 tarjetas)
  Units to allocate = Σ Left − Impossible
    sub: "<n> line items · <draft units> already proposed as draft" (n = líneas con Left > 0)
  Impossible to cover = Σ faltante por SKU
    sub: "<n> SKUs need a new purchase order" (1 → "1 SKU needs …") o "Nothing is blocked"
  Free inventory to draw on = libre warehouse (TODO el catálogo) + libre de contenedores en
    tránsito + libre de POs (decisión del cliente; sin duplicar por 4.2)
    sub: "<on hand> on hand · <in transit> in transit · <on order> on order"
  Already allocated = Σ entradas no huérfanas de órdenes abiertas, por etapa (4.3)
    sub: "<on hand> on hand · <in transit> in transit · <on order> on order"

4.9 Filtros Show + búsqueda
  Everything → todas · Needs allocation → Left > 0 · Cannot be covered → faltante > 0.
  Búsqueda: cada palabra debe aparecer en orden, SKU, producto o ref de una fuente
  asignada (sin distinguir mayúsculas). Se combina con el filtro.

--------------------------------------------------------------------------------
 7. INTERACCIONES, DATOS Y ESTADOS
--------------------------------------------------------------------------------
- Tarjeta 1 → "Needs allocation"; tarjeta 2 → "Cannot be covered"; segundo clic →
  "Everything". Clic en un chip → ese filtro.
- Buscador: filtra filas al instante (combinado con el filtro).
- Cache: se guardan solo los datos crudos (localStorage "etoile-matrix-cache-v2"; en
  Vibe puede ser monday.storage) con su hora. Validez 2 HORAS: al abrir, si hay cache
  vigente se muestra al instante; si no, se lee todo de monday. "Refresh" siempre relee
  los tableros y recalcula.
- Carga inicial: tarjetas con esqueleto animado; tabla "Loading from Monday…".
- Error sin datos: .note.warn "Monday could not be read. <mensaje>" + "Try again".
- Refresh fallido: se conservan las cifras; "Refresh failed. … Showing the figures loaded
  at HH:MM." + "Try again".
- Refresh correcto: toast "Figures recalculated with fresh data from Monday.".
- Accesibilidad: tarjetas clickeables role="button" + teclado (Enter/Espacio);
  aria-pressed en chips; foco visible.
